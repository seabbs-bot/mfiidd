Choosing a particle sampler

Particle MCMC is not one algorithm. The filter, the thing the sampler conditions on, and the thing it integrates out are three separate choices, and most named methods are one combination of them. This page draws each scheme step by step and says whether it would work for the SEIT4L model of the practical, and what you would have to write to try it.

Three choices, not one algorithm

Most of the names are a combination of these

How the filter proposes. The bootstrap filter simulates from the model and ignores the data until it weights. A guided or auxiliary filter looks at the day's count first and proposes towards it. This changes how many particles you need, not what the sampler targets.

What the sampler conditions on. PMMH updates the parameters and throws the path away. Particle Gibbs keeps a path, updates the parameters given it, and then updates the path given the parameters. One sees the filter's noise in its acceptance ratio, the other does not.

What is integrated out. If part of the state is conditionally linear and Gaussian, a Kalman filter can handle that part exactly and the particles only carry the rest. SEIT4L has no such part, which is why one family below does not apply.

Particle marginal Metropolis-Hastings

What the practical runs

Works here, and is what the committed chains use. The cost is the one the sampler page shows: the acceptance ratio carries the filter's noise, so the chain sticks, and the particle count has to be calibrated to control it.

Particle Gibbs

Keep a path, and update the parameters given it

Would work here, and the parameter step is the attraction. Given a complete path the SEIT4L likelihood is available in closed form: for a continuous-time Markov chain it is a product over transitions of the rate that fired, times the exponential of the total hazard integrated over the time spent in each state. Both are read off a Gillespie path directly, because the simulator already knows every event time and every waiting time. So the parameter update sees no filter noise at all.
The catch is the path step. Plain particle Gibbs inherits the collapse the filter page draws: the new path shares its early history with the old one, so the early parameters barely move. This is what ancestor sampling exists to fix.

Ancestor sampling

Repair the reference path's past instead of copying it, where the model allows it

This is the one that does not work with the model as it stands, and the reason is worth understanding. Drawing a new ancestor needs the probability of moving from each candidate state to the reference state in one day. The Gillespie simulator can draw from that distribution but cannot evaluate it: the day's transition density of a continuous-time Markov chain is a matrix exponential over a state space of every compartment combination. Backward simulation needs the same quantity. A tau-leaping or binomial-transition version of the model would supply it, at the cost of simulating an approximation.

SMC²

A cloud of parameter values, each carrying its own filter

Would work here, needs no density the model cannot supply, and is the one that suits a many-core machine. Each parameter particle carries an independent filter, so the work spreads across cores with no synchronisation until the parameter cloud is resampled. It also gives the marginal likelihood as it goes, which is what model comparison between SEITL and SEIT4L wants. Nothing in the course stack implements it, so this is the largest build of the four.

Better filters, same sampler

Changing the proposal inside the filter changes the particle count, not the target

Neither of these runs against the model as it stands, and it is the same obstacle both times. A guided proposal has to divide by its own density, and the auxiliary filter has to score a state against the coming count before propagating. Both call for a transition density, and the Gillespie dynamics implement simulate and nothing else, so both stop at a MethodError rather than at a judgement call.

That density is not merely unwritten. For a continuous-time Markov chain the probability of going from one compartment state to another over a whole day is a matrix exponential over every state the population could pass through. A fixed-step approximation, tau-leaping or binomial transitions, would give you one, and would make this whole family available at the cost of simulating an approximation of the model.

The bootstrap filter is the one member of the family that never needs it, because the transition density cancels out of its weights and leaves the observation density alone. That is why the course uses it, and why the calibration session buys precision with particles rather than with a better proposal.

The Rao-Blackwellised filter is the other member and does not apply for a different reason. It integrates out a part of the state that is linear and Gaussian given the rest, and SEIT4L has no such part.

The version matters. Manifest.toml resolves GeneralisedFilters 0.4.2, which is what the column above describes. Version 0.5.0 packages several of these differently, adding ConditionalSMC(BF(N)) with AncestorSampling() and BackwardSimulation() as refreshments, so the names change even where the obstacle does not. The four "no" rows are not version accidents: they follow from the dynamics implementing simulate and nothing else. Most of this column is checked by running it in pull request 154, which is where the failures above come from. GPU work exists as well, in the package's CUDA extension. It resamples on the device and expects the particles in one array, which suits a fixed-step simulator and not a per-particle Gillespie loop.

If you want one thing to try next, try particle Gibbs. The piece that has to work inside the filter already does: conditioning on a reference path runs on these dynamics, because forcing one particle down a fixed path needs no density. The sampler around it is yours to write in the pinned version, and the parameter update is exact arithmetic on a path you already simulate, which removes the filter's noise from the parameter step rather than calibrating around it. Check the path step for the collapse the filter page draws before trusting the early parameters, and note that the usual repair for it, ancestor sampling, is the row above that does not run.
